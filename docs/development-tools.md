# Форматирование, анализ и проверки перед коммитом

## Инструменты

Нужны Python 3.10+, CMake 3.24+, Ninja, CTest, компилятор, Uncrustify 0.83.0,
clang-tidy и PowerShell 7. На Windows предпочтителен MinGW64.
Пути к инструментам хранятся только в локальном Git config, не в шаблоне.
Зависимости C++ при первом запуске скачиваются CMake; offline-настройки см. README.

## Стиль

uncrustify.cfg задаёт стиль проекта: 4 пробела, отступ внутри namespace,
скобка на той же строке, T*/T& у типа, if(...), сохранение порядка include.
sp_member=ignore сохраняет пробелы вокруг ->, но не добавляет их автоматически.
Новый код пишем с object -> method(). clang-format для этого стиля не используется.

Проверка файла (путь к executable можно указать полностью):

```text
uncrustify --check -c uncrustify.cfg -f source/main.cpp
```

Явное форматирование конкретного файла:

```text
uncrustify -c uncrustify.cfg --replace --no-backup source/main.cpp
```

Hook никогда не применяет форматирование и не вызывает git add или stash.

## clang-tidy

Включены проверки типичных ошибок и статический анализатор Clang.
Массовая модернизация и правила именования не включены. Зависимости и generated
не входят в стандартную область анализа: include/, source/, tests/.
Исходники зависимостей всё равно разбираются компилятором; ошибки парсера
считаются ошибкой проверки и не подавляются.

После настройки и сборки Debug:

```powershell
pwsh -NoProfile -File scripts/run_clang_tidy.ps1 -ListOnly
pwsh -NoProfile -File scripts/run_clang_tidy.ps1 -Files source/main.cpp -WarningsAsErrors
```

Параметры: -BuildDirectory, -ClangTidy, -Files или -FilesFrom (JSON-массив),
-Scope (заменяет стандартную область), -ListOnly, -WarningsAsErrors.
Скрипт использует compile_commands.json. Для MinGW он получает target и include
от компилятора CMake, а resource headers — от Clang рядом с выбранным clang-tidy.
Несовместимый комплект инструментов нужно исправить, а не скрывать диагностику.

## Установка hook

В новом проекте сначала git init. Затем:

```text
python scripts/install_git_hooks.py --jobs 4
```

Если инструмент отсутствует в PATH, укажите его установленный executable через
--uncrustify, --clang-tidy или --powershell. Эти пути сохраняются только локально.
Если инструменты доступны в PATH, соответствующие параметры можно опустить.
Установщик проверяет инструменты, сохраняет пути, Python и число jobs в
cppTemplate.hooks.*, устанавливает core.hooksPath=.githooks.
Чужой hooksPath или существующий стандартный pre-commit сохраняется:
в этом случае установщик отказывает и требуется ручная интеграция.
Git config не переносится генератором: установку выполняют для каждого репозитория.

## Порядок проверок

Для staged-изменений собственного C++:

1. Проверка согласованности рабочих входных файлов и индекса.
2. Python-регрессии генератора и tooling.
3. Uncrustify --check изменённых файлов целиком.
4. Конфигурация и сборка Ninja/Release с BUILD_TESTING=ON.
5. CTest со всеми зарегистрированными тестами и ошибкой при отсутствии тестов.
6. Строгий clang-tidy затронутых единиц компиляции.

Заголовки сопоставляются с включающими их единицами по базе зависимостей Ninja.
Новый собственный исходник/заголовок без покрытия блокирует проверку.
Изменения CMake, шаблонов generated-заголовков, конфигураций инструментов и
скрипта анализа вызывают анализ всех собственных единиц компиляции.
Удаление исходника тоже запускает сборку и тесты. Изменения только Python/hooks
запускают Python-регрессии, документация не вызывает C++-сборку.

Все собственные входы проверок должны соответствовать индексу; частичный staging
и не добавленные новые входы блокируют hook. Это позволяет проверять рабочие
файлы без stash и без изменения индекса. Нерелевантные заметки могут оставаться
незакоммиченными. Переименования учитываются как удаление и добавление.

Hook использует отдельный work/pre-commit-build. --build-dir при установке может
выбрать другой подкаталог work/, но не build/debug или сборку IDE.
Существующий несовместимый CMakeCache не перенастраивается.
На Windows каталог выбранного CMake добавляется перед Git MSYS DLL только
в окружении проверки; глобальный PATH не меняется.

План для индекса без запуска проверок:

```text
python scripts/pre_commit.py --plan
git hook run pre-commit
```

Полная ручная проверка рабочего дерева независимо от staging:

```text
python scripts/pre_commit.py --all --plan
python scripts/pre_commit.py --all
```

--all предназначен для ручной приёмки незакоммиченной работы; Git hook запускает
обычный режим для индекса. Ошибки инструментов, сборки, тестов и анализа
возвращают ненулевой код и блокируют commit. Проверки не обходят через --no-verify.
Без установленных hooks Git сам не запускает versioned-файлы из .githooks.

## Проверка инфраструктуры

```text
python -m unittest discover -s scripts -p test_*.py -v
```

Кроме unit-тестов нужно проверять hook в отдельном сгенерированном Git-репозитории:
успешный полный запуск, отказ на неправильном формате, сохранение исходников
и индекса. Синтетические репозитории должны изолировать переменные Git вызывающего
hook, чтобы тест не менял конфигурацию настоящего репозитория.
